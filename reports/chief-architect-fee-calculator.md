## Executive Decision

**Yes. This application is fit for release, and I am opening no release gate — seventh round running.** Nothing in this document is built, so nothing in it changes the release state of what is: Round 16 and the paste work shipped, deployed as v16, `npm test` exit 0 and the debts harness 27/27 at 320/360/390. On the request itself the answer is **yes, narrowed, with the arithmetic ruled here and one question that blocks** — and it is yes for a reason the proposal states correctly in §3 and then undercuts in §5. The Round 11 entry was written to stop this application *asserting* a rate it had not been told; it was never written to stop a user *telling* it one, and its stated premise — that the lender states both amounts — is an empirical claim about the Mongolian market which the owner, whose judgement `product-strategy.md` says outranks this repository, has now corrected. That is the mechanism the *Unverified Market Assumptions* table exists to provide, firing for the second time in one day, in the opposite direction from the first. What the proposal has not earned is its own central sentence: *"Inference is a model. Arithmetic over a stated input is not."* The arithmetic it proposes needs two conventions the user did not state and the record does not contain — simple or compounding, and how a span of days becomes a count of months — and §5 concedes it knows neither. **Those are not implementation details; they are the model, and a ₮66,000 fork on a ₮1,000,000 loan is not a rounding question.** So the shape is approved, the month convention is ruled here, the interest convention goes to the owner as a single blocking question with both branches pre-ruled, and the calculator ships showing its working — because the number it produces appears in no document the user holds, which is the one property that made the paste path safe and the one that does not survive the transplant.

## Rulings on the Four Questions in §6

### Q1 — Is the Round 11 entry narrowed?

**Yes. Narrowed by exactly one shape, and the narrowing is written so it cannot expand by association in either direction.**

> **Permitted:** a rate the **user states**, consumed by a **form-time calculator** that fills an existing field, stores nothing, shows its working, and can be overridden by typing.
>
> **Still off limits, unchanged and reaffirmed:** a rate the application **infers** from data it holds; a **stored** rate field; an amortisation schedule; an assumed repayment pattern; an effective/IRR rate; a second rate on a debt card; and **the abbreviation APR anywhere in the user interface.**

Four grounds, in order of weight.

**First, the entry's premise was empirical and the owner has corrected it.** The Round 11 rejection reads, at `archive-chief-architect-round13.md:476`: *"The user chose 'only interest is a cost' over the alternatives and does not know their APR. A rate model is the accounting feature this feature was chosen instead of."* The first sentence is a claim about what Mongolian borrowers know. `product-strategy.md`'s closing line on the assumptions table is unambiguous: *"The owner of this file knows this market and the repository does not. Where the two disagree, the owner is right and this table is what gets corrected."* The owner says the lender states a monthly rate and the borrower does not know the total. **If that is true, the prohibition no longer only stops the application asserting a rate it was never told; it stops the application accepting one it was.** The proposal's §3 is right about this and it is the reason I am ruling rather than refusing.

**Second, the distinction between inference and statement is one I have already drawn twice inside this entry's own history, and it holds.** Round 13's S1 refused to let the entry expand into a prohibition on *saying what the application does*. Round 16's C2 refused to let a feature request contract it into permission for *the model it names*. This is a third object and it is on the permitted side of both lines: option B asserted a repayment schedule the application had never seen; this asserts nothing about the contract at all. The application does one multiplication over numbers the user typed and shows the result for confirmation. **The Salary Calculator is the precedent, not a novelty** — it already carries Mongolian social insurance and withholding rates, computes over stated inputs, and puts the result in front of the user. Domain arithmetic over user-stated inputs is not new in this file.

**Third, the shape stores nothing and the proposal is right that §4 is byte-identical.** `db.debts` keeps `principal`, `totalToRepay`, `date`, `dueDate`, `notes`. **No storage key, no schema field, no migration — and that prohibition is now untested for the third consecutive request about this module, which I am recording as a property of the module rather than a coincidence.**

**Fourth, rejecting would not remove the owner's problem; it would relabel it.** The fallback is a flat-fee form. A user whose lender quotes 3% a month and no fee must compute the fee to use it — the same multiplication, one step earlier, in their head, unshown and unchecked. **A rejection that moves the arithmetic from a screen that shows its working to a user who has none is not the conservative answer.** That is the decisive practical point and it is why the "reject and take the fallback" branch is not the smallest change that removes the risk.

**What I am not doing.** I am not accepting §3's claim that this is not a model. It is a small one, it is now named, and the whole of the conditions below exists because of it.

### Q2 — The not-stored reading in §4

**Confirmed. A calculator filling an existing field is not a schema change. It is not *not* a model, and the proposal conflates the two.**

Filling a form field in front of an existing handler adds no write path — the paste ruling's Q1 settled that and the reasoning holds unchanged. `db.debts` is untouched in shape. **The Round 15/16 prohibition on any new storage key, schema field or migration is not tested by this feature and stands unamended.**

But §4 also claims the paste ruling's four properties *"apply here unchanged"*, and **that is wrong on the third one, which is the one that was load-bearing.** Property 3 reads: *"Every value it writes is visible and legible in the form's own display idiom before the user taps Add Debt. A number that arrives in the field in a format the user's own typing would never produce is a number they cannot check against the message."* Its purpose was a **comparison against a document the user holds**. The paste path put the lender's own digits into a labelled field beside the lender's own message. **This path puts a number that appears in no document the user has.** Their SMS says "3% сарын хүү"; it does not say ₮1,360,000. The verification act that made the paste path safe does not exist here, and the format condition alone does not reconstruct it.

**So property 3 is replaced, not inherited: the working is the verification act.** One sentence, at the moment the fill happens, stating the rate used, the months used, the convention assumed, and the cost produced — so that what the user checks is the *inputs and the assumption*, which they do hold, rather than the output, which they do not. That is FEE-04 and it is not optional. Properties 1, 2 and 4 carry unchanged: never submits, never touches `db`/`localStorage`, and nothing is stored anywhere.

### Q3 — The drift in §5(c)

**Ruled: real, confirmed at source, **not created by this feature**, and not blocking. It is a risk I recorded three commits ago, biting exactly where I said it would. Storing the rate stays off limits. The pre-ruled answer, if it ever bites in practice, is an edit trail — not a rate field.**

This is the question I was asked to rule on most directly, so I will be precise about why it does not stop the feature.

**The drift exists today.** A user who types ₮1,360,000 and later moves the due date out three months already keeps a total that no longer matches what they were quoted. `openDebtEditModal` renders `mDebtTotal` and `mDebtDue` as independent fields and nothing couples them. Moving a due date in this application does not renegotiate a loan; the lender's total does not move because the borrower wished the date were later. **The calculator does not create a coupling — it creates an *expectation* of one in the user's head, for the length of one form session, and then the number becomes exactly the object it is today: a total the user accepted.**

**Round 16 pre-ruled this, in my own words, in the risk register:** *"A renegotiated loan still has no answer, and a rate that changes when a user edits a debt reads as the application changing its mind. `totalToRepay` as a single number with no edit trail was accepted at stage 1 and is now load-bearing for one more figure. **If it bites, the answer is an edit trail, not a rate model.**"* §5(c) is that sentence arriving. I will not overturn it three commits later to buy a schema field, and I would not buy the schema field even if the entry were open: a stored rate would make the application's total a standing claim about a contract it has never seen, which is the object the Round 11 entry actually protects against and which this narrowing explicitly does not touch.

**What makes the drift survivable is that the application never claims otherwise.** Nothing is stored, nothing is displayed after the fact, no card says "this total is 3% a month", and the working line lives and dies inside the form session. The application states its assumption at the moment it makes it and then makes no further claim. **A derived figure that escapes its derivation is a defect; a number the user accepted and the application stopped talking about is a record.** That is the line, and this falls on the right side of it.

**Two binding consequences.** The edit modal gets **no calculator** (FR6) — a rate input there would recompute a total from a rate the record does not hold, which is the drift wearing a fix. And the drift is written into the comment above the calculator as the design record, in those words, so the next reader does not "fix" it by adding a field.

### Q4 — Does §5(b), the month conversion, belong in this ruling?

**Yes. Entirely. It is ruled here and it is not an implementation choice — CODE-04's precedent is correct and the proposal was right to ask.**

Round 16 fixed a display threshold at 1,000% rather than leave it open on the stated ground that *"a threshold left open costs a round."* A term conversion that multiplies the user's principal is a larger object than a threshold. Ruled:

> **The calculator's term is whole calendar months from `date` to `dueDate`, computed with the module's existing `parseISO` idiom; any remaining days count as one further whole month; the month count is printed in the working line; and a term of zero or fewer days produces no total and says so, matching `debtTermDays`'s existing null discipline.**

**Why round up.** Rounding down records **less debt than the user owes**, and this project has twice called that direction worse than uninformative — *reassuring* — most recently at round 13 §5(b). Rounding up records more, which Round 16 rejected option B for and which the paste ruling called *"wrong in the direction of alarm, which is the direction this project is least able to detect in itself"*. Neither direction is free, so the tie is broken by **detectability**: the round-up is printed in the working line and the total is one editable field away, so a user charged pro-rata corrects it in one keystroke. A round-down would be invisible. **The rule is not "prefer the larger number"; it is "prefer the error the user can see."**

**Why this does not contradict Round 16's C2.** C2 banned month conversion *in the decoder's denominator*, because a month-rounded denominator understates short terms invisibly. These are two derivations answering two different questions: the decoder annualises a **stored ratio** over the contracted span and uses days; the calculator reconstructs a **lender's quoted monthly charge** and must use months, because that is what "3% сарын хүү" means. **Both facts go in the comment, in one sentence, because the next reader will otherwise unify them** — and unifying them silently changes either the card's headline rate or the user's stored total. FK3.

**And one fork I will not rule, because it is not mine.** §5(a) — simple or compounding — is a market question, the gap is ₮66,000 on ₮1,000,000, and `product-strategy.md` says the owner outranks the repository on exactly this class of question. **It goes to the owner as a single blocking question, with both branches pre-ruled so one answer settles the feature and no architect round is needed either way:**

> **Blocking question, one sentence to the owner:** *When a Mongolian lender says 3% сарын хүү, is the 3% charged on the original amount every month (simple — 12 months costs 36%), or on the growing balance (compounding — 12 months costs 42.6%)? And if a loan runs part of a month, does the lender charge the full month or only the days?*
>
> **Pre-ruled, so neither answer costs a round.** Simple → `total = principal + principal × rate × months`. Compounding → `total = principal × (1 + rate)^months`, and nothing else in this ruling changes. Full month → the ruling above stands. Pro-rata → the month count becomes fractional, the working line prints it to one decimal, and the round-up sentence is dropped. **In every branch the convention is named on screen in the working line and in the comment. The calculator is not written before this is answered.**

## §7 — What the proposal is not asking for

**Accepted in full, and every item on it is written onto the off-limits list below so it cannot arrive later as polish.** Not a stored rate, not an amortisation schedule, not APR in the interface, not a repayment plan, no change to `debtProblem` or to either write path, and **not a second door**.

On the last of those, one strengthening the proposal did not state and which I am making binding: *"the total remains directly typeable"* is not enough on its own, because a live calculator that keeps recomputing would overwrite what the user typed. **The user's own typing always wins over the application's arithmetic.** Any direct edit of `#debtTotal` by the user clears the rate input and removes the working line for that entry. That rule is not chosen, it is derived — the module's own comment at `:10214-10217` already says it about a different case: *"silently rewriting either number would restate what the user typed about their own money."* FN4.

## Rulings on What the Proposal Did Not Ask

**FN4 — a user edit of `#debtTotal` turns the calculator off for that entry.** Derived, not chosen: `:10214-10217` already says *"silently rewriting either number would restate what the user typed about their own money."* The user's typing wins. The rate input is cleared and the working line goes.

No existing field moves (FR11). **Pre-ruled fallback so this cannot cost a round:** if at 320px the rate input and the working line read as clutter against the family-loan helper, the **family-loan helper yields** — hidden while a computed total is showing, never deleted — and the working line stays, because the working line is the verification act and the helper is advice for a case the calculator is not in. **FN6 — the due-date helper gains no clause.** It is already four sentences and Round 16 put the last one there. The fact that the due date now also drives the total is stated in the working line, at the moment it happens, under the field it happened to — which is where this module puts every other assumption it makes. ## Architecture Strategy — next quarter

**What stays, and is not open for discussion.** Everything in the round-9 standing decision and the Round 11 through 16 supplementals and the paste-request ruling, in full, **except the single entry narrowed at Q1**. The single self-contained `expense-pwa\index.html` that runs by being opened from disk. No framework, no build step, no bundler, no component abstraction, **no new dependency** — reaffirmed against this request specifically: no date library, no decimal library, no formatter. `localStorage`, one write seam, `load()` total, quarantine before write, numbered append-only migrations. **Offline-first, mobile-first, and correctness of financial data above everything** — and this request is decided by that last clause in both directions at once: it is approved because the alternative leaves the arithmetic in the user's head, and it is conditioned because the arithmetic it does is over conventions the application had to invent. A debt figure never reaches a period-filtered surface (C38). A figure the application computed by a model of its own is labelled as such wherever it is presented as a fact about the outside world (C36). Comments state rules, never tallies (ARCH-01). A citation names the thing, not the place (C43). The Debts module's own decisions stand — refusal at the boundary rather than clamping, the delete cascade, the three capped derivations, the disclosure sentences — and I am reopening none of them.

**What changes.**

1. **The rate entry is narrowed by exactly one shape, and the narrowing is now stated in one place rather than two.** Permitted: a rate the user states, consumed by a form-time calculator that fills an existing field, stores nothing, shows its working, and yields to typing. Still off limits: an inferred rate, a stored rate, an amortisation schedule, an assumed repayment pattern, an effective/IRR rate, a second rate on a card, and APR anywhere in the interface. **Round 13 refused to let this entry expand into a prohibition on saying what the application does; Round 16 refused to let a feature request contract it into permission for the model it names; this ruling opens it by the width of one input the user types and not one millimetre further.**
2. **A new rule, and it generalises past this feature: where the application computes a number the user cannot find in any document they hold, it shows its working, and the working is the verification act.** The paste path had a document to compare against and that comparison was its whole safety argument. This has none, so the working line is not copy — it is the mechanism. Any change that removes it removes the grounds of this approval.
3. **Third application in three rounds, so it stops being a recollection and becomes the module's rule: in Debts, any figure the application produced rather than received states on screen, at the point it is produced, what it assumed to produce it.** `debtAnnualCostRate`'s sentence, PASTE-04's sentence, and now FEE-04's. In all three the wording is the load-bearing part and the arithmetic is the easy part.
4. **A market premise that a shipped comment states as a fact is corrected in the file, not only in a report, and the correction is recorded where wrong assumptions are traced.** Second time this project has had to correct a fact living inside a comment; the first was one of my own numbers.

The architect rules shapes, and `project.md` outranks the strategy on what the application IS.
