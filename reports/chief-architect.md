## Executive Decision

**Yes. This application is fit for release, and I am opening no release gate — fifth round running.** Two independent reviews of the same module returned zero Critical and zero High findings against the code as built, and the single High in the cycle (UI-01) is filed against a proposal that does not exist in the repository, which cannot block a release of what does. The shipped Debts module is the best-defended code in the file — refusal at the boundary through both doors of every rule, a delete that cascades, three derivations hardened against an observed overpayment, and a figure that says on screen whose arithmetic produced it — and its two real defects (a bell that outlives its cause, a cloud restore that leaves one screen stale) are XS repairs at the module's edges, not in its money path. What the module is not yet ready for is a fourth derived figure: its largest number is an unlabelled percentage, its block header states a count, and one comment implies a cap is uniform when it is not. Those are the three things Sprint 1 exists to make true before a second percentage lands on the same card.

## Rulings on the Escalated Questions

### E1 — §3, the no-schema-change reading

**Confirmed. Term is `dueDate − date`, derived, and `termMonths` is rejected.**

Code Review verified this at source rather than accepting the proposal's claim: `date` required and ISO-validated, `dueDate` optional and ISO-validated when present, both stored by both write paths. **The Round 15 off-limits entry — no new storage key, schema field or migration in this cycle — is not tested by this feature and stands unamended.** `termMonths` would be a field, a migration, a validator clause and a new input on a form whose field order was settled in Round 15, bought to store a number the record already implies. That is the most expensive available answer to a question arithmetic already answers.

Two binding consequences, both from Code Review's implementation notes: the function treats an absent `dueDate` and an explicit `null` identically, because pre-`dueDate` backups carry the first and both current write paths write the second; and it **must not read `db.debtPayments`**. The rate is a property of the contract, not of the ledger, and the comment says so where the function lives, so the next reader does not "fix" it.

### E2 — §4, the A/B/C/D ruling. This is conflict C2 and it is ruled in the C2 section below

**Option A, on a day-count basis. B and C are rejected. D is rejected as a schedule and replaced by a deferral with a trigger that names a change in what the application knows.** Full reasoning at C2.

### E3 — §5 row 1, "omit the rate, say nothing"

**Rejected as specified. UI-01's disposition is approved as WORK-14.**

The proposal's defence of silence is an argument about typical records; the form is an argument about every record. `dueDate` is labelled optional and its helper states only what the field does *not* do, so the field is presented as skippable to every user, including one with a non-bank loan and a term they could have entered. `product-strategy.md` puts this figure first in the build sequence and on the permanently-free side of a line the strategy calls not a risk but a line. A feature that is invisible and unexplained for whoever skipped an optional field is not permanently free; it is permanently absent for them.

**Ruled shape:** where `totalToRepay > principal` and no usable term exists, one line stands in the rate's position telling the user the one action that produces it. The gate on cost is what keeps the family case silent, which is the outcome §5 actually wanted, and it preserves the existing rule that a zero cost is omitted rather than printed as ₮0.

### E4 — §5 rows 3 and 4, the zero-length and very-short term

**Row 3: CODE-03's correction is accepted at source. The zero-length term is a supported state of the primary write path, not an import artefact — both write paths test `dueDate < date`, so `dueDate === date` is stored by the normal UI and renders as "due today" today.** The guard therefore goes in the derived figure, which returns `null` on a term of zero or fewer days, on the `showCost` precedent. **`debtProblem` is not touched, and the `<` comparisons in the two write paths are not changed to `<=`** — a debt borrowed today and due today is a real record, refusing it would break a legitimate write to protect a division, and `debtProblem`'s deliberate refusal to cross-check the two dates was ruled on and stays ruled.

**Row 4: the figure is shown, and the display is capped, not the computation.** Above a threshold the line reads "more than 1,000% a year". I am fixing the threshold at **1,000%** rather than leaving it to implementation, because a threshold left open costs a round. It is a named constant beside the function with one sentence saying it bounds what is printed and never what is computed.

### E5 — C1, the overpayment display

Ruled in the C1 section below. **The card is not capped. The ledger total is what the user typed and the application does not under-report the user's own data.**

### E6 — UI-13 and CODE-05

**UI-13 is ruled into the record: the term is the contracted span, so the rate is constant for the life of the debt and changes only when the user edits `date` or `dueDate`.** Both existing day-counts in this module measure from `todayISO()`, so today-relative is the shape a reader of this file would reach for by default; a headline figure that rose every time the screen was opened and went undefined past the due date would be un-actionable and would contradict the cleared-debt handling. This costs one sentence in the function's comment today and a round to discover later.

**CODE-05's guards do belong in a ruling rather than in implementation — and that is part of why option A wins.** A bisection with a plausible-looking ceiling returns the ceiling silently when the answer lies above it, over a worst case that `debtProblem` leaves genuinely unbounded, on the module's headline financial figure. A guard whose absence is invisible is a guard that has to be mandated by whoever rules the feature, not remembered by whoever writes it. Under this ruling no solver ships, so the guards have nothing to bind; they are preserved verbatim as pre-ruled conditions on the deferred effective-rate entry, so that if that trigger ever fires nobody needs an architect round to rediscover them.

### E7 — Dependency 5, one helper edit or two

**Two edits, and the reason is truthfulness rather than scheduling.**

The reminder clause (UI-03) is true today and ships in Sprint 1. The rate clause (UI-01) describes a feature that does not exist until Sprint 2; shipping it early would put a false sentence in a live form for a sprint, which is ARCH-01's own failure mode inverted. **The second edit is not optional and it rides the WORK-14 commit**, so the helper ends up stating both things the field actually does. If for any reason WORK-14 does not ship, the helper is correct as left.

## Conflict Rulings

### C1 — The overpayment display (UI-02 vs CODE-08, gates WORK-03)

**Ruling: UI-02's direction wins. The card figure is not capped. CODE-08's secondary branch — the comment that implies the cap is uniform — is corrected in the same commit, and it is binding. Both filed severities stand exactly as filed.**

This is settled by a rule I have already written and made permanent. A row cap that omits records from a transaction list is off limits *"permanently — the app may be slow; it may not under-report the user's own data."* Capping the card's `paid` figure is the same act one level down: printing ₮1,300,000 where the user recorded ₮1,400,000 is the application making a false statement about money the user handed over, in order to make two of its own figures agree. The summary tile's cap is defensible on different grounds — an aggregate that exceeded the sum of its own agreements would be a worse lie — but a cap that is right in one place is not therefore the module's rule, and the comment at `:9529-9538` currently reads as though it is.

So: the card stays literal, the tile stays capped, one gated line in the module's existing helper voice reconciles them where `debtPaid(d.id) > totalToRepay`, and the comment states the rule as *two figures with two jobs* rather than one uniform cap. That is the only shape both reports accept, and the Engineering Manager was right to notice it without resolving it.

**Conditions, binding.** No derivation changes and no cap is reopened. One site, one line, gated on a condition that is false for every correctly entered debt. The line names the excess and tells the user what to check; it does not apologise and does not offer to correct anything. The existing harness fixture at `tools\harness\debts.js:855-887` — which already seeds this exact state and asserts nothing about the card — gains one assertion that the card reports the ledger total, so the rule ruled here cannot drift back by accident. That assertion rides the same commit.

### C2 — The §4 option disposition (UI-06 vs Code Review's §4 response, gates WORK-16 and WORK-17)

**Ruling: Option A, computed from days. Option B is rejected. Option C is rejected. Option D is rejected in its stated form and replaced by a deferral whose trigger is a change in what the application knows rather than a date on a roadmap.**

Neither reviewer is overruled, because neither claimed this ground. Both were right within their remit and the decision turns on a third thing that is mine: **what the application is entitled to claim about a contract it has never seen.**

**First, the standing record, which nobody cited and which governs.** The Round 11 supplemental put *"an interest-rate / APR field, or an amortisation schedule"* on the off-limits list, and Round 13's S1 read that entry precisely: it is a rejection of a **model**, not of saying what the application does. Option B is the rejected object by name. It assumes a repayment schedule the application does not record, discounts assumed installments back to the principal, and solves for a rate — that is an amortisation model, arriving as the headline figure of the module the prohibition was written about. Option C is B plus a second figure. **An off-limits entry may not be overturned by a feature request that does not know it exists, and I will not overturn this one, because the reason it was written is still true: this module was chosen over a rate model, and the user does not know their APR.**

**Second, and this is the part that decides it independently of the record.** Correctness of financial data outranks everything here. Option A is a statement whose truth conditions the stored data fully determines: the cost, as a share of the amount borrowed, per year of the contracted term. It is true for a bullet loan, true for an installment loan, and true for a loan repaid in whatever ad hoc pattern this application actually records. Option B is true **only if** the borrower repays in equal monthly installments, which the application does not record, does not model anywhere else, and has explicitly deferred (scheduled repayments, standing deferral, trigger intact). A module that refuses to model a schedule everywhere else, and then prints a headline figure that only holds if a schedule it invented is the one in force, is making the strongest claim in the application out of the thinnest evidence in it. For a bullet loan it would **overstate by roughly a factor of two**, by the proposal's own arithmetic — and overstating is not the safe direction merely because the mission is to expose understatement. A finance application that a user can catch being wrong in either direction has lost the thing it runs on.

**Third, on the proposal's sharpest sentence — "understating a predatory rate is worse than showing no rate."** That sentence is correct about a *rate* and it is not correct about *this figure*, because the fix is not arithmetic, it is labelling, and this module already owns the practice. Option A understates only if it is presented as the interest rate. Presented as what it is — a share of what was borrowed, per year — it understates nothing, because it is not a claim about the rate on the outstanding balance at all. **Nothing in this ruling permits the word APR, and nothing permits a bare percentage.** The wording constraint in WORK-16 is load-bearing and is the condition on which A is approved.

**Fourth, UI-06's objection to A — "a number that confirms the framing the screen exists to break has no behaviour-changing content left in it" — is right about the level and wrong about the comparison, which is the gap the proposal actually stated.** §2's worked case is two loans with identical tugrik cost over 12 months and 3 months, rendered identically today. Under A they read 30% and 120%. That is the discrimination §2 asked for, delivered in full, by one expression with no new failure mode beyond the term guard.

**Fifth, on D.** Both reviewers are right that publishing the lender's figure and then doubling the headline number for the same debt, with no change to the user's data and no restatement record anywhere in this application, is the most expensive option over time. So D is rejected **as a schedule**. What replaces it is not "later"; it is a condition: the effective rate becomes computable from a record rather than from an assumption on the day this application records a repayment schedule. That day is the standing deferral for scheduled repayments. If it arrives, the figure changes because the application learned something, which is explicable on screen; until it arrives, there is nothing to defer to.

**What ships, then:** one expression, `cost ÷ principal × 365 ÷ days`, per CODE-04. No month conversion anywhere — the month-rounded denominator understates short terms, which are the predatory ones, and it does so invisibly. **365 fixed, not 365.25, one constant, stated once.** No solver, no iteration, no bracket, no convergence path, no new class of failure in the module's headline figure.

### C3 — The proposal's cost estimate (informational, gates WORK-14)

**Ruling: the proposal's §3 estimate that the cost of omitting the rate is "close to zero" is not accepted, and UI-01's reading is adopted.** The Engineering Manager is right that this is not a disagreement between the two reports — it is a claim in the design request that one report contradicts and neither supports. A design request's own estimate of its own cost is an input, not a finding, and it is the cheapest thing in any cycle to leave unchecked. Ruled at E3.

## Architecture Strategy — next quarter

**What stays, and is not open for discussion.** Everything in the round-9 standing decision and the Round 11 through 15 supplementals, in full. The single self-contained `expense-pwa\index.html` that runs by being opened from disk. No framework, no build step, no bundler, no component abstraction. `localStorage`, one write seam, `load()` total, quarantine before write, numbered append-only migrations. **Offline-first, mobile-first, and correctness of financial data above everything** — this round is the clearest application of that last clause the project has had, because it decided a feature's arithmetic against a figure that would have looked more impressive. A debt figure never reaches a period-filtered surface (C38). A collection that must never reach a total keeps its own array (C39). A figure the application computed by a model of its own is labelled as such wherever it is presented as a fact about the outside world (C36). Comments are the design record and state rules, never tallies (ARCH-01). A citation names the thing, not the place (C43). The Debts module's own decisions — refusal at the boundary rather than clamping, the delete cascade, the three capped derivations, the disclosure sentence under the summary card — are correct and I am reopening none of them.

**What changes.**

1. **The Debts module gains a fourth derived figure and no new storage.** The rate is a stock, pure over one debt record, derived from the contract and never from the ledger. That purity is not tidiness: the payoff plan is item 2 of the build sequence, it iterates rates over scenarios, and a function that reaches into `db` makes item 2 pay for this one's convenience.
2. **The off-limits entry on rate models is narrowed by exactly one shape, and the narrowing is written down so it cannot expand by association in either direction.** Permitted: a ratio of two stored amounts over the contracted term, labelled by what it is a share of. Still off limits: an interest-rate or APR input field, an amortisation schedule, an assumed repayment pattern, and any second rate. Round 13's S1 refused to let the entry expand into a prohibition on saying what the application does; this round refuses to let a feature request contract it into permission for the model it names.
3. **A derived figure that cannot be computed returns `null` and the screen says what would produce it**, where the missing input is one the user could supply and the figure is one the product exists to show. That is WORK-14 generalised, and it is the correct reading of an optional field that turns out to be load-bearing.
4. **A display threshold is not a computation.** Where an arithmetically correct figure reads as a rendering fault, the print is bounded with an explicit "more than" and the arithmetic is left alone. The threshold is named once beside the function.

**What is off limits this quarter.** Everything on the round-9, 11, 12, 13, 14 and 15 lists, unchanged. **Five additions or reaffirmations:**

- **An amortisation model, an assumed repayment schedule, an effective/IRR rate, or the abbreviation APR anywhere in the user interface.** Reaffirmed at C2 and now with a named trigger that is the only way back.
- **A second rate figure on a debt card**, in any form, including behind a detail sheet or a disclosure. The card's rate copy is closed at one sentence.
- **Capping, truncating or otherwise reducing any figure that reports what the user recorded.** The row-cap prohibition generalised at C1: the application may show a user a figure they did not expect; it may not show them a smaller one than they entered.
- **A numeric solver anywhere in `expense-pwa\index.html`** without its own ruling. The file has none today, there is no local convention to inherit, and the first one arrives with CODE-05's guards attached or it does not arrive.
- **Any new storage key, schema field or migration** — carried from Round 15 unchanged, and confirmed at source this round as untested by this feature.

**Risks I am recording, not scheduling. None of these is a finding, and no reviewer raised any of them as one.**

- **Mine, from C2.** Ruling A means the application's headline rate agrees with the lender's quoted figure in level. If the wording constraint in WORK-16 is weakened in implementation — if the sentence ever reads as "the interest rate" rather than as a share of what was borrowed per year — then the proposal's sharpest objection becomes true and this ruling becomes wrong. The wording is the load-bearing part, not the arithmetic, exactly as Code Review's future-risk note says about `debtInterestPaid`. I am recording it so that whoever weakens that sentence knows what they are spending.
- **Mine, from C2.** A user who compares our figure against their paperwork will find them agreeing, and may conclude the loan is fine. The discrimination between a 3-month and a 12-month loan at identical tugrik cost is what this ruling buys and it is the gap §2 actually stated; the shock of the effective figure is not bought, and will not be until a repayment schedule is recorded.
- **Carried from Code Review.** A renegotiated loan still has no answer, and a rate that changes when a user edits a debt reads as the application changing its mind. `totalToRepay` as a single number with no edit trail was accepted at stage 1 and is now load-bearing for one more figure. If it bites, the answer is an edit trail, not a rate model.
- **The required-field rule is kept in this module and knowingly unkept in two others** (the goal-contribution sheet and the income/expense edit sheets). Recorded so the next cycle that opens either one knows it inherits an item, and so the fix is derived from each handler rather than swept.
- **At least one more stale line-number citation lives in the application file, outside this module.** ARCH-01 has been applied to `tools/` and to one site in `renderDebts`; the file-wide pass is real and unscheduled.
- **The bell badge still has no single refresh seam** — five debt sites plus seven goal and expense sites each remember it individually. Not worth an abstraction for twelve sites; worth knowing that the next module with reminders makes it three lists to remember.
- **`renderDebts` walks the payment ledger roughly seven times per debt and sorts with a comparator that derives twice per comparison.** Not a defect at this user's scale and not optimised now. It becomes real when the payoff plan iterates scenarios over the same figures, and the cheap fix when it arrives is one `Map` built once per render, which `debtPaid`'s shape already supports.
- **Every string in this module is a literal, including the three helper sentences whose exact wording carries the module's honesty — and this ruling adds a fourth.** The language layer is item 3 of the build sequence and these are the hardest strings in the application to translate and the most costly to get wrong. It still needs its own scoped proposal and its own ruling before a line of it is written.
