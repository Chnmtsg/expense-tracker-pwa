## Rulings on the Five Questions in §5

### Q1 — The field: `settledOn`, one optional ISO date, and the no-migration reading

**Approved as proposed, in all four parts, and the name stands.**

**The object.** One optional ISO date string on the debt record, meaning exactly what §2 says it means: **the user says this debt was finished on this day.** Not a payment, not an amount, not a claim about what the lender charged or accepted.

**The name.** `settledOn` is approved and every alternative is closed. I note the departure from the record's `date` / `dueDate` suffix and I am ruling it deliberate rather than accidental: those two are properties of **the contract**, and this is the date of **an event the user asserts**, and a different suffix carries that difference at every read site. I am not renaming it to `settledDate`, and I want the reason on the record because it is the general one: **renaming a correctly-named field is my preference substituted for the proposer's, and it buys nothing.** What the name must never become is a state: **`settled`, `isSettled`, `cleared`, `settledFlag` or any boolean is off limits** (SR1). A date says what happened; a flag says what the record is, and a flag is the shape this fence was written to keep out.

**The no-migration reading, confirmed in four parts.**

1. **Append-only, no step.** Confirmed at source above, and reinforced by a standing rejection the proposal did not cite: a `SCHEMA_VERSION` bump with nothing to transform is already off limits. `migrations` gains nothing. `SCHEMA_VERSION` does not move.
2. **Absent on every existing record.** True by construction — nothing writes it but the act in SET-03.
3. **Absent and explicit `null` identical.** Binding, and it is the `dueDate` lesson from E1 carried verbatim. The write path writes `null` on reversal and **never `delete`**, matching `d.dueDate = dueDate` where `dueDate` is `|| null`; the predicate treats absent, `null` and malformed identically.
4. **One `debtProblem` clause in `dueDate`'s shape.** Approved, in the sibling's own words: present and malformed is refused, absent or `null` is normal. **It is NOT cross-checked against `r.date` or `r.dueDate` in `debtProblem`** — the existing comment three lines above already rules this class: *"an importer rejecting a whole backup over it would destroy more than it protects, and nothing derived divides by the gap."* The date ordering is enforced at the boundary the user is standing at, in the write path, refused and never clamped, on the module's own two-door rule.

**Two additions that are mine, because nobody else would have made them and both are load-bearing.**

**The predicate is shape-tested, and its failure direction is fixed.** `debtProblem` has never run over cloud-loaded records. `!!d.settledOn` would let any junk string mark a debt finished, and a debt wrongly reported finished is the application under-reporting an obligation the record holds — the row-cap error of C1, one level down, on a boolean. So the predicate tests the shape it needs: a string matching `ISO_DATE_RE`, anything else is **not settled**. Defensive in its own right, per WORK-13's binding consequence, and **its failure direction is toward the state that keeps the debt live.**

**The date is stated by the user, never stamped by the application.** This decides Q3 as much as it decides Q1. If the act writes `todayISO()`, what the record holds is the date of the *click*, stored under a name that says *settlement* — which is C36 exactly: do not compute from one fact and present another as evidence. The user settled on a day; the user states which day. That is why a bare confirm dialog cannot carry this act (SR13) and why Q3 rules the shape it does.

### Q2 — §3's gap: can `ED1` ship without `ED2`?

**Yes. `ED1` ships alone, and it is not blocked on `ED2`. Do not put a larger scope back to the owner. But the gap the proposal found is real and it is in a different place than §3 puts it, and that changes what is inside this commit.**

**First, the correction, and it is the most useful sentence in this document.** §3 says a settled card would carry a figure whose only honest label is the saving. **It would not.** `.debt-remaining` is the card's only site for `debtOutstanding`, and it is already gated on `cleared`: once the cleared test absorbs the fact, the card prints **"✓ Cleared"** and the difference does not appear on it at all. The proposal's premise — *"that leaves a settled card carrying a figure"* — is false at source, and the instinct behind it is nevertheless right, because the figure survives **somewhere else**:

| Site | What it renders | Under `ED1` |
|---|---|---|
| Summary tile **"Still owed"** | Σ `debtOutstanding` | **Aggregates ₮240,000 of an obligation that does not exist.** This is §5.5, and it is the original harm at the aggregate level. |
| **Payment sheet** helper | "… — **₮240,000** still owed" | States an obligation the user has said is finished. |
| **Payment sheet** `data-qa-exact` chip | A one-tap quick amount of **₮240,000** | **The sharpest site in this document. It offers to record a payment of money the user does not owe, on the module's own affordance for the final payment.** SN1. |
| **History modal** helper | "… — **₮240,000** still owed" | Same claim, second modal. |
| Card `.debt-remaining` | suppressed by `cleared` | Nothing owed. |
| Bell `sub` | skipped by the reminder gate | Nothing owed. |

**So the thing `ED1` needs is not the saving. It is the predicate, at every site that renders the words "still owed".** That is one rule with several readers — the shape WORK-08 already established in this module — and it is one piece of work, not two. It is inside `ED1`, and §6's *"no change to `debtOutstanding`"* does not fence it, for the reason I stated in the early-settlement ruling and am now applying: **a disclaimer in a proposal binds the proposal, not the future.** The **function** `debtOutstanding` is not changed (SR5) — the proposal is right that `totalToRepay − paid` is a true statement about the record — but its **consumers**, at the sites where they put the word *owed* on screen, adopt the predicate. That distinction is the whole of §3, correctly placed.

**Second, what `ED1` leaves behind, stated plainly so nobody discovers it in review.** With a settled debt excluded from "Still owed", the three tiles stop reconciling: paid plus owed no longer equals the total agreed, by exactly the saving. **The user is left with a question and not with a false statement.** The summary card never displays the agreed total, so there is no visible arithmetic contradiction; what there is, is a card reading "₮1,120,000 paid of ₮1,360,000 · ✓ Cleared" with nothing saying where the difference went. **The answer to that question is `agreed − paid`, which is `ED2`, and the only copy surface it could land on — the `.debt-totals` helper block — is closed at three sentences permanently and a fourth is on the off-limits list.** That is `ED2`'s content and `ED2`'s round. I am not opening the block here and I am not printing the figure here (SR7, SR8).

**Third, the decision rule.** The alternative to shipping `ED1` alone is leaving in place a red overdue chip that grows daily, a card above live debts for ever, an aggregate that reports money as owed, a quick-amount chip offering to pay it, and **an OS notification about a debt the user finished, under a comment in their own application saying it does not do that.** Those are false statements. The gap is an unanswered question. **Correctness of financial data outranks everything, and an unexplained truth beats an explained falsehood every time.** `ED1` ships.

**`debtInterestPaid` is not touched, confirmed.** §3 is right and its reasoning is right: on a settled-early debt "Cost so far" reports roughly ₮296,471 where ₮120,000 plus a fee was paid, the function is doing exactly what its comment says, and capping or special-casing it would be ER3 in miniature. **Not fixed, not capped, not gated on the new predicate** (SR6). It stays a recorded risk.

### Q3 — A, B or C

**All three are rejected as stated, and I am ruling a fourth shape: the control from A, a sheet rather than a dialog for the act, and B's field-emptying idiom for the reversal. §4 invited "or reject all three" and this is that branch.**

**Why C fails as stated.** A confirm dialog cannot take a date the user states. It would stamp `todayISO()`, and a stamped date stored under a name that says *settlement* is the application asserting a fact it was not told — C36, and the exact class this whole line of rulings exists to protect. **C's instinct is right: the act states what it will do and is deliberate. Its instrument is wrong.** (SR13.)

**Why B fails.** Three grounds, any one sufficient. It puts **the one act in this module that silences an OS notification** behind a screen a user opens to correct a typo, which is a consequence hiding behind an unrelated label. It is undiscoverable at exactly the moment the harm is on screen — and Round 16's only High was precisely this shape: a feature reachable only by whoever found an optional field is permanently absent for everybody else. And the modal's own comment closes its field list at five while the template already renders six, so option B would be a seventh field arriving through a door whose sign is already wrong. (SR14. B survives only as `SD1`'s pre-ruled shape, and not as the home of the act.)

**Why A as stated fails, and how it is repaired.** A is "a fifth control on the card", and my own `EN4` pre-ruled: *"if `ED1` ever fires, it is not a fifth always-visible button on every card."* **I am narrowing `EN4` by exactly one shape and I am saying so rather than quietly stepping over it.** `EN4` was written without the source in front of me and without an instrument named; its content is a **layout** objection, and the layout question is cheap, measurable and has a one-declaration answer. So `EN4` becomes what it always meant: **a fifth control on the debt card does not ship unmeasured.** It is narrowed by one shape and not one millimetre further — no text label, no second row of controls by design, no new class, no new primitive.

**The shape that ships.**

> **Reaching it:** one icon-only control in `.debt-actions`, on `button.goal-icon-btn` **unchanged** — no new class, no new component. It carries `title` and `aria-label`, matching the three controls beside it. **The glyph is ✓**, which is the card's own existing vocabulary for this state ("✓ Cleared"), so the control introduces no new symbol; it must not collide with 📜 ✎ ✕ 📅 📝. **It is never rendered with a text label** — a text button costs on the order of 90px against an icon's 44px, and that is the difference between fitting and not.
>
> **The act:** a sheet on the **existing** `editModal`, reached only from that control, with its own `editCtx.kind` and its own title — the shape `openDebtPaymentModal` already uses, so it costs no new modal, no new primitive and no new dismiss behaviour. **One field: a date, defaulted to `todayISO()`, `min` the borrow date, and on a debt already settled it opens showing the stored date.** Plus one helper sentence (below). Nothing else. No amount (SR12), no notes, no second field.
>
> **Reversal (§5.4): empty the field and save.** This is `mDebtDue`'s own documented idiom — *"Cleared by emptying the field, which is how an agreed date gets removed"* — so one sheet serves both directions and **correcting a settlement date is free rather than deferred.** It writes `null`, never `delete`. **No confirm dialog in either direction:** the delete carries one because it cascades and is irreversible; this is reversible in the same two taps that made it, and ceremony that buys nothing is noise.
>
> **The write:** a new **branch** on the existing save seam, not a new seam. `debtAdd` and the `editCtx.kind === 'debt'` branch are unchanged, which is what §6 means and what I hold this to (SK5). It writes `settledOn` and nothing else — never `totalToRepay`, never `db.debtPayments`, not one tugrik of what the user recorded. It **refuses** a date earlier than the borrow date, at the boundary, refused and not clamped, and it names the record that blocks it, exactly as the two existing debt handlers do. It does **not** invent a future bound: nothing derives from this date and nothing divides by it, and a refusal that protects nothing costs a legitimate record. It calls `save()`, then `renderDebts()`, then **`updateBellBadge()`** — SN6, and this is not optional: a sixth debt write site that forgets the badge reproduces the one defect Round 16 found that a user meets in normal use.
>
> **The sentence.** One line in the module's existing helper voice, inside the sheet, stating **what marking it settled will do**: the application stops reporting it as outstanding and stops reminding about it. **It states a consequence; it does not reassure, does not apologise, does not congratulate, and does not state a saving, an amount, or anything about what the lender did or agreed** (SR7, ER10 carried). **The sheet's copy is closed at this one sentence, permanently, on the way in** — the `.debt-totals`, "Left After Plan", PASTE-04 and FEE-04 precedents, applied before three rounds of growth rather than after.

**I am deliberately NOT making that sentence its own item, contra PASTE-04 and FEE-04, and the reason matters.** In both of those the sentence *replaced a missing verification act* and was the ground of the approval. Here nothing is inferred and nothing is modelled: the user is stating a fact about their own record. The sentence discloses a consequence, it lives inside the sheet body its own item builds, and splitting one string out of the template it sits in is bookkeeping rather than a commit boundary. Work not done is the cheapest work there is.

**The width, and the pre-ruled fallback, so this cannot cost a round.** `npm run debts` runs at `--width 320` and asserts `E_page_overflow === 0`; it already measures `.debt-actions button.goal-icon-btn`. Run it at 320, 360 and 390 after SET-03. **If the fifth control overflows at any of them, the fix is one declaration — `flex-wrap: wrap` on `.debt-actions` — and no architect round is needed.** That is derived, not chosen: `.debt-foot` and `.debt-totals` both already wrap, and the latter's comment states the reason. **The act does not fall back to the edit modal**; a layout problem gets a layout answer.

### Q4 — Reversibility

**Ruled at Q3 and restated here because §5.4 asked it as its own question. Reversible, by the same sheet, by emptying the date.**

It is a second write into the same fact and **not** a second write path: one branch, one field, two directions, one handler. The proposal was right to flag it and right that clearing the field is the obvious answer; the reason it is also the *correct* answer is that the module has already documented this exact idiom for `dueDate` and a second dialect for it would be one to learn for no reason. Reversal restores the prior state exactly, because nothing else was ever written.

**One consequence I am recording rather than defending against.** A user can mark a live debt settled and silence its reminders. **That is their record and the application does not second-guess it** — an app that argued with the user about whether their debt is finished would be inferring, which is the whole thing this ruling refuses. The mitigations are that the act is deliberate, that the sheet says what it will do, and that undoing it is two taps. It is a foot-gun with a safety, and it is recorded in the risk register rather than engineered against.

### Q5 — The summary tiles

**Ruled: a settled debt contributes ₮0 to "Still owed". The other three tiles are unchanged. The helper block is not opened.**

"Still owed" is the only one of the four that makes a claim about an **obligation**; a debt the user has said is finished owes nothing, and an aggregate that says otherwise is §5.5's original harm at the one surface the user glances at first. **"Borrowed in total", "Paid back so far" and "Cost so far" are not touched**: they state what was borrowed, what was handed over, and what the application's own allocation says it cost, and a settlement falsifies none of them.

**The existing three helper sentences stay exactly as written and none becomes false.** The ungated one — *'"Still owed" includes anything you agreed to pay on top of what you borrowed'* — describes what the figure includes, not which debts it counts. **No fourth sentence** (SR8). The reconciliation gap this opens is `ED2`'s content, and `ED2` will arrive as a question about where a figure or a sentence can go on a card whose copy is closed — which is exactly why its presentation was deliberately not pre-ruled.

- *Not an amount alongside the date* — accepted and permanent. SR12.
- *No second settled-like state anywhere else in the application* — accepted. Goals, planned expenses and recurring series get nothing from this. SR16.
- **Clarification, binding, and it is the same one I made last time: a disclaimer in a proposal binds the proposal, not the future.** §6 is accepted for this request; it is **not** a prohibition on the consumers of `debtOutstanding` adopting the predicate, which Q2 rules is inside `ED1`. ## Architecture Strategy — next quarter

**What stays, and is not open for discussion.** Everything in the round-9 standing decision, the Round 11 through 16 supplementals, the paste-a-loan, fee-calculator and early-settlement rulings, **in full, with no entry narrowed by this document except the two named below.** The single self-contained `expense-pwa\index.html` that runs by being opened from disk. No framework, no build step, no bundler, no component abstraction, **no new dependency** — reaffirmed against this request specifically: no date library, no state library. `localStorage`, one write seam, `load()` total, quarantine before write, **numbered append-only migrations**. **Offline-first, mobile-first, and correctness of financial data above everything** — and this request is decided by that last clause twice: once in approving the field, because the alternative is the application going on making a statement it knows is false, and once in refusing 100% on a settled card, because a tidy figure that overstates repayment is the same error as a cap that understates it. A debt figure never reaches a period-filtered surface (C38). A collection that must never reach a total keeps its own array (C39). A figure the application computed by a model of its own is labelled as such (C36). Comments state rules, never tallies (ARCH-01). A citation names the thing, not the place (C43). **This morning's rate narrowing is reaffirmed at exactly the width it was granted and is not widened by one millimetre.**

**What changes.**

1. **The storage entry is narrowed by exactly one shape, and the narrowing is written so it cannot expand by association.**
   > **Permitted:** one **optional field on an existing record**, written **only by an explicit user act**, absent on every existing record, absent and explicit `null` treated identically, refused by the validator only when present and malformed, and needing no migration step because there is nothing to transform.
   >
   > **Still off limits, unchanged and reaffirmed:** a new **collection** or storage key; a `SCHEMA_VERSION` bump; a **migration step**; a **required** field; a field written by **inference, by default, or by any path other than the user's own act**; a **stored rate**; a **status flag or boolean** on any financial record; and a second write path into `db.debtPayments`.
2. **A prohibition that has never been tested is not known to be load-bearing — and the test is whether the thing it protects is still being protected.** This entry held for four consecutive requests, each time because the request did not touch it. It is now tested and it bends by one field. What it protects is schema churn, migrations, and fields the **application** writes. **It was never written to stop the application recording a fact the user states**, and a prohibition that would have done so is a prohibition that had stopped being about its own reason.
3. **A predicate's failure direction is fixed toward the state that keeps the obligation live.** C1's row-cap rule, generalised from figures to booleans: where the application cannot tell whether a debt is finished, it says it is not — because the error it can afford is telling a user they still owe money they have paid, and the error it cannot afford is telling them a debt is finished when the record says otherwise.
4. **One claim, one meaning, at every site that renders it.** "Still owed" is a claim, not a variable. The function that computes it may stay exactly as it is; every surface that puts the **word** on screen adopts the predicate. WORK-08 one level up, and it is why SET-02 is one commit and not nine.
5. **A card control does not ship at 320px unmeasured, and when it fails the answer is a declaration, not a redesign.** `.debt-foot` and `.debt-totals` already wrap and their comments say why; a third row in the same card joining them is the cheapest possible fallback, and pre-ruling it is what stops a layout question costing an architect round.
