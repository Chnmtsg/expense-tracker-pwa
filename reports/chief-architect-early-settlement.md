## Rulings on the Four Questions in §5

### Q1 — Is a proportion of the user's own agreed cost over two stored spans outside the inference prohibition?

**No. It is a rate model by another name, and I am saying so as plainly as I was asked to: on this ground the request ends.** Three independent grounds, any one of which is sufficient.

**First, the algebra. The prohibition is on a model, not on an identifier.** Round 13's S1 read the entry as a rejection of a model; Round 16's C2 refused to let a feature request contract it into permission for the model it names; this morning's Q1 permitted *a rate the user states* and reaffirmed that *a rate the application infers from data it holds* stays off limits. Now factor §2's expression:

> `cost × monthsHeld ÷ contractedMonths`  ≡  `principal × [ cost ÷ (principal × contractedMonths) ] × monthsHeld`

The bracketed term is a monthly rate derived from the two stored amounts. FR3's words, this morning, were *"the application deriving a monthly rate from the two stored amounts and presenting it as the lender's."* This derives exactly that and then declines to print it. **Not naming a model's parameter does not make the model absent; it makes it unstated — which is worse under C36 and worse under the rule I wrote eight hours ago, that where the application computes a number the user cannot find in any document they hold, it shows its working.** There is no working to show here that would not be the rate.

**Second, the truth condition, which is Round 16's C2 with one word changed.** C2 rejected option B because it was *"true only if the borrower repays in equal monthly installments, which the application does not record."* §2 is true only if the cost accrues **evenly over the contracted term**, which the application also does not record and cannot check. A `totalToRepay` typed from a lender's paper may carry a flat origination fee, an insurance charge, an admin charge, compounding, or front-loaded interest; each produces a `cost` that does not accrue evenly, and the record is identical in every case. **A calculator the user may or may not have used, storing nothing, means the application cannot even tell which of its own `totalToRepay` values came from a simple monthly model.** The module refuses to model a schedule everywhere else; it does not get to model an accrual here.

**Third, and decisively, the direction of the error — and the evidence is in the comment the proposal quotes.** `debtInterestPaid`'s comment states, as a fact about the world, *"Charging interest first is what the lender actually does."* If lenders front-load, even allocation **understates** the cost attributable to the months held and therefore **overstates** the saving. §4 then adds a second, unbounded overstatement from the unknown fee. **Two independent biases, both reassuring, stacked on one figure, in a module whose design record twice rules that reassurance is worse than uninformative.** The proposal found one of them. The file contains the other and the proposal cited that very comment for a different purpose.

**On the `debtInterestPaid` precedent, which is §2's load-bearing sentence.** *"Proportional allocation of this exact cost is also already this module's shipped practice… the same idea over a different denominator, not a new kind of claim."* The first half is true and the second is false, and the distinction is the whole ruling. `debtInterestPaid` allocates across **the user's own recorded repayments** and says on screen that it is *"spread evenly across your repayments, so it may not match your lender's own statement."* It is a statement about the application's bookkeeping, labelled as the application's. §2 allocates in order to say **what the lender would have charged and what the user therefore saved** — a counterfactual about a third party's conduct under a contract the application has never seen. Identical arithmetic; categorically different claim. **C36 is the rule and it lands on the far side of this line.** EK1.

**What I am not saying.** I am not saying the arithmetic is wrong. On a loan entered through the shipped calculator under simple monthly interest it is exactly right. I am saying the application cannot know which loans those are, and a figure that is right when an unverifiable condition holds is a model.

### Q2 — A, B or C, or reject all three?

**A rejected. B rejected permanently. C is the only admissible shape, and it is not mine to authorise.**

**Option A — the predictive saving on a live debt — is rejected on four grounds.** It rests entirely on the Q1 model, so it dies with it. It is a claim about **what a lender will accept**, which is a stronger assertion than any this application makes about anything. The unknown fee is unbounded and runs against the user, so the number is wrong in the reassuring direction at the exact moment the user is deciding whether to act on it — this is not a figure that informs a decision, it is a figure that could produce one. And it collides with the roadmap: *"settle this today and the cost stops at X, saving Y"* is a single-debt payoff projection, and `product-strategy.md`'s build sequence item 2 is **the payoff plan** — *"pay this much more, finish this much sooner, save this much."* **A builds one corner of a ruled roadmap item, ahead of it, on a model, where item 2 would then inherit it.** EK5. The proposal's own instinct that A is *"furthest from what was literally asked"* is correct and it is the least of A's problems.

**Option B — treat "paid at least principal plus time-attributable cost" as settled — is rejected permanently, and it is the worst of the three.** It is the Q1 model promoted from describing a debt to **deciding** one. The application would display a stored obligation as discharged against a stored figure that says otherwise, showing **less debt than the record holds** — which is the direction round 13 refused when it rejected a rounding that recorded less debt than was owed, and the mirror of the row-cap rule generalised at C1 (*the app may show a user a figure they did not expect; it may not show them a smaller one than they entered*). **A derived figure may describe a record. It may never decide that a record's obligation is discharged.** That goes on the off-limits list as a rule, not as an item.

**Option C — the user marks it settled — is the only shape in which nothing is inferred, and it is the only one that also makes the requested figure exact.** This is the part neither the proposal nor the owner's choice had in view, so I will state it in full:

> The application already holds both numbers. It holds what was agreed (`totalToRepay`) and it holds what was actually handed over (`debtPaid`). **The saving is `agreed − paid`. One subtraction over two stored quantities. No rate, no accrual, no allocation, no model — and the early-settlement fee is already inside it**, because the fee was part of the money the user paid and recorded. The figure §4 says can never be known is the one quantity this shape does not have to know.

The proposal's own worked example is the proof, and it is also EK2: §3 posits a settlement of ₮1,120,000, which is exactly `principal + cost × 4 ÷ 12` — **an example constructed with a zero fee, by the model it was offered to justify.** Put a ₮50,000 fee in it and the user pays ₮1,170,000: the model still says the cost was ₮120,000 and the saving ₮240,000, both wrong; `agreed − paid` says ₮190,000 saved, exactly right. **The model is right only in the example that was built from it. The subtraction is right in every case.**

**So the one thing standing between the owner's request and an exact, model-free answer is that the record cannot say a debt is finished — and §6 forbids the field that would say so.** That is the ruling, and it is why this goes back rather than forward.

**On re-opening the owner's choice, and the limit of my authority.** The division was written into the FEE strategy this morning: the owner corrects market facts and rules product; the architect rules shapes. **Whether a settle act is a good use of the user's attention is the owner's call and I am not making it.** What I am ruling is that inside "show what was saved and change nothing about the record" **there is no admissible shape at all** — A and B are both models and both fail, and no third model-free option exists, because no automatic test can distinguish "settled early" from "still owes the difference" without the fact that distinguishes them. **The owner chose between three options believing the set was non-empty. It was empty. They are entitled to know that before the request is dropped.** This is not the owner being overruled and it is not a ruling being overturned by a product decision; it is the architecture reporting that a constraint and a request are incompatible, which is exactly what it is for.

### Q3 — Does an unknowable early-settlement fee make any saving figure unshippable, or merely caveated?

**Both, and which one depends entirely on whether the figure is predictive or retrospective. This is the sharpest distinction in the request and the proposal did not draw it.**

**A predicted saving is unshippable, and a caveat cannot repair it.** The lesson the proposal correctly extracts from FEE-04 is that the wording is load-bearing — but it misreads *which* wording works. FEE-04's working line is safe because it names **the inputs and the conventions, which the user holds**: their own rate, their own dates, whole months, the original amount. The user can check every term in it. A fee caveat names **a quantity the user does not hold, the application cannot bound, and nobody can check at the moment it is shown.** Those are not the same instrument. **A caveat can name an assumption. It cannot stand in for a quantity.** Attach *"your lender may also charge a settlement fee we do not know"* to a bold ₮240,000 and what the user carries away is ₮240,000; the sentence is the part that is forgotten, and the error it half-discloses runs in the reassuring direction, on top of the front-loading bias from Q1. **A number whose error term is unbounded, undisclosed in size, and biased toward good news is not made shippable by a sentence. It is made deniable.** That is the opposite of what this project means by showing its working.

**A retrospective saving does not have the problem at all, and owes no caveat.** `agreed − paid` is net of the fee by construction. There is nothing unknown left in it. **The fee is only unknowable before it is charged** — which is the whole reason the answer to this request lives after the settlement and not before it, and is a second, independent ground for rejecting option A.

**§4's constraint is confirmed in the form it was stated and strengthened in one place:** whatever ships must name what it does not know **in the same sentence as the figure** — and where what it does not know is a quantity rather than an assumption, the correct response is not to name it but to **not print the figure.**

### Q4 — The month convention: one rule or two?

**One rule, and the rule was never the rounding direction. It is stated at FEE Q4 and I am reaffirming it verbatim: *the rule is not "prefer the larger number"; it is "prefer the error the user can see."***

Applied to the calculator, that rule produces rounding **up**: the round-up is printed in the working line, the month count is named, and the total sits one keystroke away in an editable field. The error is visible and free to correct.

Applied to a **held** term derived from a stored record, the same rule produces **neither direction** — because there is no input field, no working line, no moment of entry, and no document in the user's hand stating a month count. Both roundings are invisible. **A convention that exists to make an error detectable has nothing to attach to, and a derivation on which no rounding rule can be satisfied is a derivation that does not ship.** That is a second and independent ground for Q1's refusal, arrived at from the opposite end.

**So the two treatments are not two rules rounding opposite ways. They are one rule, meeting two cases, and failing the second one.** Had I ruled "round up here too, because up is conservative here as well", I would have adopted **"prefer the larger number"** as the convention — which is the rule I explicitly refused this morning, arriving by the back door and carrying an outcome as its justification. **Direction-of-conservatism is not a convention. Detectability is.** Recorded here so nobody derives a rounding rule from an outcome ever again.

**One binding consequence regardless of everything else.** `debtAnnualCostRate` takes days with 365 fixed; `feeTermMonths` takes whole months rounded up; the comment above the calculator already says why the two must not be unified. **A third term derivation does not enter this module.** ER7.

## §6 — What the proposal is not asking for

**Accepted in full, every clause written onto the off-limits list below — and the third clause is what ends the request, which is worth saying plainly because it is the single most useful sentence in this document for the owner.**

- *Not a stored rate* — accepted, reaffirmed, ER8/ER9.
- *No change to `debtProblem`, `debtOutstanding`, `debtInterestPaid` or either write path* — accepted for this request. **One clarification, binding: a disclaimer in a proposal binds the proposal, not the future.** If ED1 ever fires, reading a settled fact necessarily touches `debtOutstanding`'s consumers, and this sentence is not a prohibition on that. It is a prohibition on **this** request touching them, which it must be, because the only way this request could have touched them is with the model.
- *No new storage key, schema field or migration* — **accepted, and this is the clause that makes the request unsatisfiable.** Fourth consecutive request about this module that does not test the entry, and the **first one where not testing it is what leaves the question unanswerable.** An honest close on a finished debt is a stored fact or it is a model, and the proposal fenced itself off from the fact. Recorded as a property of the request, not a criticism of it — §3 says so itself, honestly, and was right to.
- *Not a repayment schedule; the standing deferral untouched* — **confirmed at source.** The effective-rate deferral's trigger is *the day this application records a repayment schedule*. A dated fact about an event that already happened is not a schedule of payments that have not. **It does not fire, and if ED1 ever ships, a settlement date must not be read as the first entry of one.** ER12 fences it.

## Conflict Rulings

There is no Engineering Manager report and therefore no recorded conflict list. **There are also no reviewer findings this cycle and so no Critical finding to approve or overrule; I am stating that rather than leaving the obligation silent.** These are the six collisions I found between the proposal, the standing record and the source. Each is ruled.

### EK1 — §2's `debtInterestPaid` precedent

**Ruling: the precedent is real for the arithmetic and false for the claim, and the claim is what was being licensed.** `debtInterestPaid` allocates the cost across **the user's own recorded repayments** and says on screen that it is the application's own even spread which *"may not match your lender's own statement."* §2 allocates the same cost in order to assert **what the lender would have charged** — a counterfactual about a third party. Same expression, different object, and C36 governs the second: *a figure the application computed by a model of its own is labelled as such wherever it is presented as a fact about the outside world.* **Here the model cannot be labelled into safety, because the label would have to name a rate the application invented.** This was §2's load-bearing sentence and it does not hold.

### EK2 — §3's worked example against §4's own premise

**Ruling: §3's arithmetic assumes the fee §4 says cannot be known is zero, and the example was therefore built by the model it was offered to validate.** ₮1,120,000 is exactly `1,000,000 + 360,000 × 4 ÷ 12`. With any non-zero fee the settlement is larger, the model's answer does not move, and the model is wrong by the fee — in the reassuring direction, permanently. **Recorded separately from Q1 because it is the cleanest available demonstration that the model's apparent correctness is circular**, and because `agreed − paid` is right in exactly the cases the model is wrong.

### EK3 — §4 against the comment it quotes

**Ruling: the comment the proposal cites for its honesty argument contains the fact that defeats its arithmetic, four lines above the sentence quoted.** *"Charging interest first is what the lender actually does."* If lenders front-load, even allocation understates the cost of the months held and overstates the saving — a second reassuring bias, independent of the fee, already recorded in this application's own design record. **§4 identified the direction of the danger correctly and then underestimated it by one bias.** Ruled at Q1, ground three.

### EK4 — §2's "the settlement date already exists and needs no new field"

**Ruling: the field exists; the fact does not — and the claim is self-defeating in exactly the case the feature is about.** Every `db.debtPayments` entry carries a `date`, confirmed at source. But "the day a debt was paid off is the date of the payment that cleared it" identifies a **clearing** payment, and `cleared` is `debtOutstanding(d) === 0`. **For an early settlement the payment never clears the debt, so the settlement date is precisely the one the record cannot point to.** The date is present as data and absent as a fact, which is the same distinction §3 draws about the debt itself and did not carry back into §2. The proposal was right that no new **input** is typed; it was wrong that no new **fact** is needed.

### EK5 — Option A against `product-strategy.md`'s build sequence

**Ruling: A is a fragment of build-sequence item 2, arriving outside it, on a model, and it is rejected partly for that.** Item 2 is *"the payoff plan… pay this much more, finish this much sooner, save this much"* — item A is that sentence over one debt. The paste ruling's K4 established that a request off the sequence is not rejected for being off it; **this is the different case, of a request that lands *inside* a sequenced item before that item is scoped, and would leave it inheriting a model it could not then remove.** The payoff plan builds on the decoder and on what the record holds. It does not get a predictive engine pre-installed by a feature that was asking about the past.

### EK6 — §6's third clause against §3's problem

**Ruling: the disclaimer list forbids the only thing that answers the problem, and that is why the request cannot be completed as written.** Recorded separately from Q2 because whoever reads this next will otherwise conclude the request failed on its arithmetic alone. It did fail on its arithmetic. **It would also have failed with perfect arithmetic**, because a debt settled early has nowhere to put an exact figure either. §3 said so itself, in the right words, and did not connect it to §6.

## Rulings on What the Proposal Did Not Ask

Five. Each is a consequence of the same missing fact, and together they change the size of the question the owner is answering. **None is a finding — no reviewer raised any of them — and I am stating them as the ruled scope of §3's problem, not as new work.**

**EN1 — `debtInterestPaid` is already wrong about an early settlement, by roughly two and a half times, in the alarming direction.** On §3's own numbers the card and the tile report **₮296,471** of "Cost so far" where the cost actually paid was ₮120,000 plus the fee. The function is doing exactly what its comment says and is not defective; **the module's most behaviour-relevant figure is simply describing a record that does not represent the event.** No fix is owed and none is approved — capping or special-casing it would be ER3 in miniature.

**EN2 — the bell is the serious one, and nobody traced it.** `computeReminders` skips a debt only on `debtOutstanding(d) <= 0`, under a comment that reads *"Cleared debts are skipped: a settled debt is not overdue, and a reminder that cannot be acted on is the reminder `nextPlannedDue` was rewritten to stop firing."* **An early-settled debt is never skipped: it produces a bell item and an OS notification, with an urgency class, about a debt the user finished, indefinitely.** That is the module's own stated rule failing for this exact case, and it is the reason §3 is a product problem rather than a display quibble. **It is not a finding, it is not fixed here, and it must not be fixed by inference** — gating the reminder on a model is ER3 with a notification attached.

**EN3 — three more surfaces, same cause.** An early-settled debt never sinks below cleared debts in the list; it keeps `deadline-danger` and an "overdue Nd" chip that grows every day, in a module whose due-chip comment exists specifically to stop the screen chasing a user about a debt it reports as finished; and `pctLabel` reads 82% for ever on a debt that is fully repaid. **One missing fact, nine surfaces, one repair — which is the argument for ED1 and against every alternative.**

**EN4 — the card foot already carries four controls.** Any settle act lands there or in the payment sheet, and at 320px that is a real layout question rather than a detail. **Pre-ruled only this far: if ED1 ever fires, it is not a fifth always-visible button on every card.** The shape is part of its own request; the constraint is recorded now so the request does not arrive assuming a button.

**EN5 — `debtProblem` cannot help here and no one should expect it to.** It validates shape, not truth, and a debt that was settled early is shape-valid in every respect. **The only thing that can distinguish the two states is the user**, which is the whole of Q2 stated one more way.

## Architecture Strategy — next quarter

**What stays, and is not open for discussion.** Everything in the round-9 standing decision, the Round 11 through 16 supplementals, the paste-a-loan ruling and the fee-calculator ruling, **in full and with no entry narrowed by this document.** The single self-contained `expense-pwa\index.html` that runs by being opened from disk. No framework, no build step, no bundler, no component abstraction, **no new dependency** — reaffirmed against this request specifically: no date library, no decimal library, no finance library. `localStorage`, one write seam, `load()` total, quarantine before write, numbered append-only migrations. **Offline-first, mobile-first, and correctness of financial data above everything** — and this request is decided by that last clause end to end, because every shape it proposed would have improved how the application *sounds* about a loan at the cost of what it can *defend* about one. A debt figure never reaches a period-filtered surface (C38). A figure the application computed by a model of its own is labelled as such wherever it is presented as a fact about the outside world (C36). Comments state rules, never tallies (ARCH-01). A citation names the thing, not the place (C43). The Debts module's own decisions stand and I am reopening none of them.

**What changes.**

1. **The rate entry is not narrowed further, and the reaffirmation is the point.** This morning's narrowing was one shape wide — a rate the user states, consumed at form time, stored nowhere, showing its working. **Eight hours later a request arrived for a rate the application derives, arguing it was not one. It is one.** A narrowing granted is not a precedent for the next narrowing, and an entry that opens by the width of each successive good argument is not an entry. **Still off limits, unchanged: an inferred rate whether or not it is printed, a stored rate, an amortisation schedule, an assumed repayment pattern, an assumed accrual pattern, an effective/IRR rate, a second rate on a card, and APR anywhere in the interface.** The word **accrual** is the one addition, and it is added because this request found the gap.
2. **A new rule, and it is the most portable thing here: the application may allocate its own bookkeeping; it may not model a counterparty's.** `debtInterestPaid` spreads a cost across the user's own repayments and says on screen that it is doing so. Any allocation performed in order to state what the **lender** would have charged, accepted or done is a model of a contract the application has never seen — **and the arithmetic is identical on both sides of that line, which is exactly why the line has to be written down rather than recognised.** ER10 is its enforcement.
3. **A record that cannot represent an event is repaired by recording the event, not by inferring it.** This is the ruling generalised and it is worth more than the ruling. When the application cannot tell two states apart, the answer is the one fact that distinguishes them, asked of the only party who holds it — not a rule that guesses which state it is in. Options A and B are both the guess; C is the fact; and the fact is also, incidentally, exact where the guess is biased.
4. **Detectability, not direction, is the rounding rule — restated, and now with a case where it produces "neither".** A convention that exists to make an error visible has nothing to bind where there is no input, no working line and no document in the user's hand. **A derivation on which no rounding rule can be satisfied does not ship.** And an outcome is never a justification for a convention: had "round up because up is conservative here too" been ruled, "prefer the larger number" would have become the rule by the back door.
5. **A disclaimer in a proposal binds the proposal, not the future.** §6 is accepted in full for this request and is not a prohibition on ED1 ever reading a settled fact. Recorded because §6's clauses are about to be quoted back at whatever comes next.

**What is off limits this quarter.** Everything on the round-9, 11, 12, 13, 14, 15 and 16 lists, the paste ruling's list and the fee ruling's list, unchanged — including the amortisation model, APR in the interface, a stored or inferred rate, a rate-period selector, a calculator in the edit modal, a third way to fill `#debtTotal`, `class="money-input"` on any input that is not whole tugrik, a second rate on a debt card, any cap that under-reports what the user recorded, a numeric solver without its own ruling, a fifth runner, a second probe, a fifth static predicate, widening `check-escaping.mjs`, `<details>` nested more than one level, any parser that writes to a collection, a general "paste anything" entry point, cloud vision, and every mechanical sweep. **Four additions:**

- **Any figure stating what a lender would have charged, would accept, or would have done.** ER10. The application states what the user agreed and what the user paid.
- **Any display that reports a stored obligation as discharged on the application's own arithmetic.** ER3, permanently. A derived figure may describe a record; it may not decide one.
- **A third term derivation in the Debts module.** Days for the rate, whole months for the calculator, and no third — the existing comment's warning is only maintainable while there are two.
- **Recording a balance the user did not pay as a payment, for any reason.** ER6. It is the cheapest-looking fix in this whole area and it is a false financial record.

**Risks I am recording, not scheduling. None of these is a finding, and no reviewer raised any of them as one.**

- **Mine, from EN2, and it is the largest.** If the owner answers no, the application will continue to send an OS notification about a debt its user finished, indefinitely, under a comment stating that it does not do that. Nothing is misstated — the record does not hold the fact — but **the cost of "leave the record alone" is not a stale number on a card; it is a notification, and the owner should be told that before they decline.** That is the whole of why this goes back rather than stopping.
- **Mine, from EN1.** "Cost so far" overstates an early settlement by roughly two and a half times. The function is correct, its label is honest, and the figure is still the most misleading thing on the card for this one user. **It is not to be capped, special-cased or gated on a model.**
- **Mine, from Q1.** I have now refused, in one day, both a request to widen this entry and a request to argue past it, and the second one was better argued than the first. **The pattern to watch is not that the entry is under attack; it is that the module keeps producing genuinely good reasons to add a model, because it holds two numbers and a span and that is almost enough for one.** It will not stop, and the answer will keep being the same one.
- **Mine, from ED1.** If it ever fires, it tests a prohibition that has held for four consecutive requests, and it does so for the right reason rather than the usual one. **A prohibition that has never been tested is not known to be load-bearing.** It gets its own request and its own ruling, and the fences in ED1 exist so that request cannot arrive shaped as a status flag, a schedule, or a second write path into `db.debtPayments`.
- **Mine, from ES-01.** The assumptions table now carries three owner-stated market facts added in one day, each of which decided something. **The mechanism has fired three times and worked three times. If one of those facts is wrong, three features are traceable to it, which is precisely the property the table was built for.**
- **Carried unchanged.** `totalToRepay` has no edit trail and is load-bearing for four things. Every string in this module is a literal and the language layer needs its own scoped proposal. The bell badge has no single refresh seam. `renderDebts` walks the payment ledger roughly seven times per debt. The required-field rule is kept here and knowingly unkept in two other modules. At least one stale line-number citation lives elsewhere in the application file. The add form stands at ten controls and the next field on it should expect a scope question rather than an approval.

## Final Recommendation

**Put one question to the product owner, take `ES-01` while you wait, and write not a line of anything else.** The question is not the one the proposal was built around, and it is short: ***when you pay a lender off early, do you want to be able to mark that debt finished on the day you settled it — recording that date and nothing else — so the application stops saying you still owe the difference?*** That single fact is the only thing standing between this request and an exact answer, because with it **what you saved is what you agreed to pay minus what you actually paid — fee included, nothing assumed, nothing modelled** — and without it there is no honest figure at any price, which is the finding of this ruling. Tell them plainly what "leave the record alone" costs, because it is more than a stale number: the debt sits above live ones for ever, the due chip stays red, "Cost so far" reads ₮296,471 where ₮120,000 was paid, and **the bell keeps sending a notification about a debt they finished**, under a comment in their own application that says it does not do that. **Yes means `ED1` returns as its own scoped design request with the fences in its row binding, and `ED2`'s subtraction follows it in a separate piece of work. No means the request ends at `ES-01` and the state is accepted knowingly and recorded as such — which is a legitimate answer and cheaper than most.** Either way `ES-01` is owed today: one row in `D:\3_Claude\PowerApps\knowledge\product-strategy.md`'s assumptions table for the fact the owner stated, and one comment in the Debts module of `D:\3_Claude\PowerApps\expense-pwa\index.html` stating the rule that a finished debt this module cannot see is a finished debt all the same. **The sentence I want carried out of this ruling is the one that decided Q1 and Q2 together: when this application cannot tell two states apart, the answer is the fact that distinguishes them, asked of the one person who has it — because every model that would have guessed instead was biased toward telling the user they had saved money, and a figure that is wrong in the reassuring direction is the single thing this module was built to stop.**
